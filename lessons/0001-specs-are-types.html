Specs Are Types

The simplest specification in Lean is the type of a function.

🔗 Mission Connection

Your goal: "Write specifications in Lean so LLMs generate code that provably conforms."
Before you can write complex specs, you need to understand the fundamental unit of specification in Lean: the type.

A function's type signature (input types → output type) is a specification. It says: "Given inputs of these shapes, I produce output of this shape." The Lean compiler checks every implementation against its type — automatically, always, without fail.

This is your spec checker.

1. What is Lean?

Lean is two things fused into one:

  • A functional programming language — like Python, but with a much more powerful type system
  • A proof assistant — it can prove that programs satisfy their specifications

For your mission, the key feature is this:

Lean's compiler checks every program against its specification automatically.
If a function claims to return a Nat (natural number) but tries to return a String, the compiler refuses to build. No runtime errors. No type mismatches escaping to production.

This is very different from Python. In Python, you can write:

def add(x, y):
    return x + y  # Is it numbers? Strings? Lists? Who knows!

Python doesn't check. The bug surfaces at runtime — possibly in production. In Lean, you write:

def add (x : Nat) (y : Nat) : Nat :=
  x + y

The : Nat after each argument and after the ) are type annotations. They say: "I expect two Nats and promise to return a Nat." Lean's type checker verifies this contract at compile time.

2. Your First Lean Commands

Open the existing file Kata/Basic.lean — you already have a working function there. Let's use two diagnostic commands to inspect it:

#eval — run any expression

Like typing into a Python REPL. Add this line at the bottom of Kata/Basic.lean:

#eval hello "World"

Then build and run from your terminal:

docker exec lean_ci lake build Kata

You won't see output yet — #eval is only visible when you run an interactive session or the file through lean directly. (We'll use tests to see results.)

#check — inspect any type

This is your most important tool. Add to Kata/Basic.lean:

#check hello

This will tell you the type of hello:

hello : String → String

Read this as: "hello is a function from String to String."

💡 Key Insight: Read Types as Specifications

The type String → String is a specification. It says:
"Given any String, this function produces a String."
Lean guarantees every call to hello returns a String — no exceptions, no None, no surprises.

3. Functions are Pure (No Hidden Surprises)

In Lean, functions are pure. This means:

  • Same input → same output, every time (no mutable state)
  • No side effects (no printing, no file I/O, no database writes)
  • No null or None sneak attacks
  • No exceptions thrown

Why does this matter for specifications?

A pure function's type is a complete specification of its behavior.
If a function is pure and type-checks, what you see (the type) is what you get (the behavior). There are no hidden effects, no implicit state, no runtime crashes.

4. Basic Types

Here are the types you'll use most often:

TypeMeaningExamplesPython equivalent
NatNatural numbers (0, 1, 2, …)0, 42, 1000int (but unbounded)
IntIntegers (…, -2, -1, 0, 1, …)-5, 0, 7int
StringText"hello", s!"Hi, {name}"str
BoolBoolean (note: lowercase)true, falsebool (case: True/False)

⚠️ Python-to-Lean Traps

  • true/false are lowercase in Lean (Python uses True/False)
  • No None or null — every variable always has a valid value
  • No if as a statement — if is an expression that returns a value
  • Function arguments are separated by spaces, not commas: add x y, not add(x, y)

5. Your First Exercise: Write a Function from a Spec

Here's the workflow you'll use throughout these lessons:

  1. I give you a specification (a type signature)
  2. You write the implementation in Kata/Basic.lean
  3. You run the tests to see if Lean agrees your code meets the spec

✏️ Exercise 1.1: double

Specification:

def double (n : Nat) : Nat :=
  -- your code here

What it should do: Return n + n for any natural number n.

Add this function to Kata/Basic.lean (after the hello function).

Run the tests:

docker exec lean_ci make tests

The tests will print something like:

double:
  ✓ returns 0 when given 0
  ✓ returns 10 when given 5

If you see all ✓, your code matches the spec. If you see ✗, fix and try again.

Solution (try yourself first!) 
def double (n : Nat) : Nat :=
  n + n

✏️ Exercise 1.2: isPositive

Specification:

def isPositive (n : Nat) : Bool :=
  -- your code here

What it should do: Return true if n is greater than 0, and false if n equals 0.

Hint: Use if n > 0 then true else false or a match expression.

Run the tests: Same command as above. Tests for this function are already in the test file.

Solution (try yourself first!) 
def isPositive (n : Nat) : Bool :=
  if n > 0 then true else false

Or with pattern matching:

def isPositive : Nat → Bool
  | 0 => false
  | _ => true

6. What Happens When You Break the Spec?

Lean's type checker is strict. Try writing this in Kata/Basic.lean:

def broken (n : Nat) : String :=
  n + 5  -- type error!

When you run lake build, you'll get:

type mismatch
  n + 5
has type
  Nat
but expected
  String

Lean is saying: "You promised me a String but gave me a Nat. That violates the specification."

This is the core of your mission. Once you write a specification as a Lean type:
  • An LLM can generate implementation code
  • Lean's compiler checks the implementation against your spec
  • If it compiles it conforms — no ambiguity, no drift, no runtime surprises
