Executable Specs — Lean as the Oracle

Your Lean functions don't just describe what correct looks like — they compute it.

🔗 Mission Connection

Your mission: "Write specifications in Lean so LLMs generate code that provably conforms."

In Lesson 1, you learned that a function's type signature is a specification. Now level up: the function body is a specification too — it's an executable oracle that computes the exact correct output for any input.

This is the key insight for your AI pipeline: You don't just describe what correct looks like in Lean — you compute it. Then you compare the LLM's output against Lean's computed answer. No ambiguity.

1. Recap: Your Functions Are Already Specs

In Lesson 1, you wrote two functions:

def double (n : Nat) : Nat := n + n

def isPositive (n : Nat) : Bool := n > 0

We said the type signature was the spec: Nat → Nat means "takes a Nat, returns a Nat." But the body is also a specification — it defines what the correct output is for every possible input.

💡 Key Insight: Executable Specifications

A specification can be executable — you can run it and get the expected answer. This is called an oracle: a reference implementation that always produces the correct output.

In your AI pipeline, the Lean oracle computes what the LLM's code should produce. Then you compare:

Lean oracle output  ==  LLM implementation output

If they match for enough test cases, the LLM's code is correct.

2. From Tests to Oracles

Look at your existing test for double:

LSpec.test "returns 10 when given 5" (double 5 = 10)

This test contains the oracle value directly: 10. But where did 10 come from? You computed it in your head: 5 + 5 = 10.

Now imagine you're testing against a spec that's too complex to compute in your head — say, "validate this JSON response against a 20-field schema with business rules." You'd rather let the computer compute the expected answer.

That's what double itself does:

#eval double 5   -- Lean prints: 10

Your function is the oracle. Instead of hard-coding expected values in tests, you can write:

LSpec.test "matches oracle for 5" (double 5 = double 5)  -- trivial
LSpec.test "some impl matches oracle for 5" (myImpl 5 = double 5)  -- meaningful!

The second form is powerful: double 5 computes the expected answer automatically, no matter what n is.

3. The Oracle Pattern

Here's the pattern for spec-driven AI development:

-- Step 1: Write the specification as an oracle function
def doubleSpec (n : Nat) : Nat :=
  n + n

-- Step 2: Compute expected outputs for test inputs
#eval doubleSpec 0    -- 0
#eval doubleSpec 5    -- 10
#eval doubleSpec 42   -- 84

-- Step 3: Write a validator that tests any implementation against the oracle
def validateDouble (impl : Nat → Nat) : Bool :=
  impl 0 = doubleSpec 0 &&
  impl 1 = doubleSpec 1 &&
  impl 5 = doubleSpec 5 &&
  impl 42 = doubleSpec 42

-- Step 4: Test the validator itself
#eval validateDouble doubleSpec           -- true  (oracle matches itself)
#eval validateDouble (fun n => 0)         -- false (wrong implementation)

✏️ Try This in Your REPL

You don't need to add this to Kata/Basic.lean — just follow along mentally. But if you want to, add a #eval line to your kata file and run:

docker exec lean_ci make tests

Look at the output. Lean computes doubleSpec 42 and prints 84. That's your oracle at work.

🔬 Why This Matters for AI

An LLM can generate code in any language — Python, JavaScript, Go, Rust. Lean doesn't care. You write the oracle in Lean, the LLM generates the implementation in Python, and you check:

# In Python, after running the LLM-generated function:
assert my_double(5) == 10  # where 10 came from Lean's oracle

# Or better: dump test cases from Lean, run them in Python
# test_cases.json: [{"input": 5, "expected": 10}, ...]

This is how Qed works: Lean computes the oracle, the LLM generates code, and a test harness checks the match.

4. Your New Exercise: max

Time to apply the oracle pattern to a new problem. Open Kata/Basic.lean and find the Lesson 2 exercises section (already added for you).

You'll write three things:

  1. maxSpec — the oracle. A function that returns the larger of two natural numbers.
  2. maxImpl — an implementation that should match the spec.
  3. validateMax — a validator that checks any implementation against maxSpec.

✏️ Exercise 2.1: Write the Oracle — maxSpec

Specification:

def maxSpec (a b : Nat) : Nat :=
  -- your code here

What it should do: Return whichever of a or b is larger. If they're equal, return that value.

Examples:

  • maxSpec 0 0 → 0
  • maxSpec 0 5 → 5
  • maxSpec 5 0 → 5
  • maxSpec 3 7 → 7
  • maxSpec 42 42 → 42

Hint: Use an if expression. In Lean, if a >= b then a else b is valid (it's an expression, not a statement).

Run the tests:

docker exec lean_ci make tests
Solution (try yourself first!) 
def maxSpec (a b : Nat) : Nat :=
  if a >= b then a else b

✏️ Exercise 2.2: Write the Implementation — maxImpl

Specification: Same behavior as maxSpec — return the larger of a and b.

def maxImpl (a b : Nat) : Nat :=
  -- your code here

Note: This simulates what an LLM would generate. You can write the same logic as maxSpec, or a different approach (pattern matching, nested if, etc.). The tests check that maxImpl matches maxSpec for all test cases — exactly how your AI pipeline will work.

Solution (try yourself first!) 
def maxImpl (a b : Nat) : Nat :=
  if a > b then a else b

Note: a >= b vs a > b — both work because if a = b, either branch returns a = b, which is the same value. But a >= b is more efficient (one comparison instead of two).

✏️ Exercise 2.3: Write the Validator — validateMax

Specification:

def validateMax (impl : Nat → Nat → Nat) : Bool :=
  -- your code here

What it should do: Test impl against maxSpec for at least 5 representative inputs. Return true only if all tests pass.

It should:

  • Return true when given a correct implementation (like maxSpec itself)
  • Return false when given a wrong implementation (like fun _ _ => 0)

Hint: Use && (logical AND) to chain multiple checks:

impl 0 0 = maxSpec 0 0 && impl 0 5 = maxSpec 0 5 && ...
Solution (try yourself first!) 
def validateMax (impl : Nat → Nat → Nat) : Bool :=
  impl 0 0 = maxSpec 0 0 &&
  impl 0 5 = maxSpec 0 5 &&
  impl 5 0 = maxSpec 5 0 &&
  impl 3 7 = maxSpec 3 7 &&
  impl 7 3 = maxSpec 7 3

This covers: equal inputs (0,0), first larger (5,0), second larger (0,5 and 3,7), reversed (7,3). A wrong implementation like fun _ _ => 0 will fail on any case where the answer isn't 0.

6. What the Validator Catches

Let's see what happens when the validator catches a bug. Imagine an LLM generates this implementation:

def buggyMax (a b : Nat) : Nat := a  -- always returns a

Your validator would catch it:

validateMax buggyMax
-- Checks:
--   buggyMax 0 0 = maxSpec 0 0  → 0 = 0  ✓
--   buggyMax 0 5 = maxSpec 0 5  → 0 = 5  ✗  --> returns false

Lean tells you: this implementation does not match the spec. No ambiguity. No "looks about right." The oracle is the final authority.

💡 The Full Pipeline Vision

You now have all the pieces for the core AI development loop:

  1. You write: an oracle function in Lean (the spec)
  2. LLM writes: an implementation in Python (or Lean, or any language)
  3. You check: validate the implementation against the oracle using representative test inputs
  4. If it fails: the LLM tries again (or you give it the failing test case as feedback)
  5. If it passes: the implementation is verified correct for all tested inputs

In later lessons, we'll cover how to prove correctness for all inputs (not just the ones you test). But for most practical AI development, testing against a representative oracle is already a huge win.

What You Learned

  • Your Lean functions are executable specifications (oracles)
  • An oracle computes the expected output for any input — no manual computation needed
  • The oracle pattern: write a spec function, use #eval to compute expected values, write a validator to check implementations
  • A validator is a function that takes an implementation and returns true/false based on whether it matches the oracle
  • You applied this pattern: maxSpec (oracle) → maxImpl (implementation) → validateMax (validator)
  • Oracles work across languages — Lean computes, Python executes, comparison reveals correctness

New Glossary Terms

  • Oracle — an executable reference implementation that always produces the correct output
  • Validator — a function that checks an implementation against an oracle for selected test cases
