From Testing to Proving — The First Theorem

Your validator tests a handful of inputs. A theorem tests every single one.

🔗 Mission Connection

Your mission: "I can read and understand basic Lean proofs, and write simple ones myself."

This is the moment Lean does something Python literally cannot. You already know how to test specific cases (Lesson 2). Now learn how to prove a property for every possible input — and have the compiler check it.

qed has 70+ proofs of its own correctness. This lesson is the smallest possible step toward reading them.

1. The Limit of Testing

Your validateMax function checks maxImpl against maxSpec for 5 specific inputs:

-- (0,0), (1,2), (2,1), (5,5), (10,3)

What if there's a 6th input pair where maxImpl is wrong? Your validator won't catch it. You'd need to add that case too. And the 7th. And the 8th.

This is the fundamental limitation of testing: you can only check finitely many inputs. Python stops here.

Lean takes the next step: you can write a theorem that is quantified over all inputs (infinitely many), and the compiler verifies the proof. No gaps.

2. The theorem Keyword

A theorem looks just like a def — but instead of returning a value, it states a proposition and gives a proof:

deftheorem
Defines a functionStates a proposition
Body is a computationBody is a proof
#eval runs it#check shows the proposition

Here's the simplest possible theorem in Lean, using double from Lesson 1:

💡 The Theorem

theorem double_eq_add_self (n : Nat) : double n = n + n :=
  rfl

Read this aloud: "For every natural number n, double n equals n + n."

The proof is rfl — short for reflexivity. It says: "These two sides are the same by definition."

double is defined as n + n. So double n and n + n are literally the same expression. The proof is trivial because the compiler can see they're identical.

3. Testing vs. Proving — See the Difference

Testing says: "I checked 5 inputs."
Proving says: "I checked all inputs."

Let's compare side by side:

-- TESTING: checks specific values (FINITE)
#eval double 0      -- 0
#eval double 5      -- 10
#eval double 42     -- 84
-- What about double 1000? You'd need another #eval.

-- PROVING: checks ALL values (INFINITE)
theorem double_eq_add_self (n : Nat) : double n = n + n := rfl
-- This single theorem covers EVERY Nat: 0, 1, 2, ... , ∞
-- The compiler verified it once. Never needs re-checking.

🔬 This Is Where Lean > Python

Python can test double(5) == 10 — one input.
Python cannot assert double(n) == n + n for every n and have the compiler verify it.
Python has no theorem keyword. It has no proof checker.

Lean does. This is the smallest possible step into the territory Python cannot follow.

5. What #check Shows You

Add this line after the theorem:

#check double_eq_add_self

It will print:

double_eq_add_self (n : Nat) : double n = n + n

This is the type of the theorem — which is also the proposition it proves. In Lean, a theorem's type IS the proposition it states. A proof is a value of that type. This is the Curry-Howard correspondence at work.

✏️ Exercise 3.1: Prove the Same for hello

Below your double_eq_add_self theorem, add a second theorem:

theorem hello_greets (name : String) : hello name = s!"Hello, {name}!" :=
  rfl

Before you add it, predict what #check hello_greets will print.

Then add it and run lake build to confirm.

Then run make tests to confirm all existing tests still pass.

Answer

#check hello_greets prints something like:

hello_greets (name : String) : hello name = toString "Hello, " ++ toString name ++ toString "!"

The proposition is "for every name, hello name equals the interpolated greeting." The proof is rfl because hello name is defined as s!"Hello, {name}!" — Lean elaborates string interpolation into concatenation, but both sides are still definitionally the same.

6. What Happens When You Try rfl Too Early?

rfl only works when both sides are definitionally equal — the compiler can tell they're the same just by unfolding definitions.

Try this (you don't need to add it permanently):

-- THIS DOES NOT COMPILE:
theorem maxSpec_self (a : Nat) : maxSpec a a = a :=
  rfl

This fails because maxSpec a a expands to if a > a then a else a. Whether the result equals a depends on whether a > a is false — which is true, but it's a fact that needs proving. The compiler can't just see it by unfolding definitions. You need a deeper proof, which you'll learn soon.

Key distinction:
  • rfl works when both sides are syntactically the same after computation
  • When the equality is true but requires reasoning (like a > a being false), you need a tactic proof — coming in the next lesson

What You Learned

  • Testing checks finitely many inputs — always incomplete
  • Proving checks infinitely many inputs — complete, verified by the kernel
  • theorem states a proposition; the body is a proof
  • rfl proves equalities that are true by definition
  • A theorem's type is the proposition it proves
  • Python cannot do this — this is the smallest place where Lean wins

New Glossary Terms

  • Theorem — a proposition whose truth is checked by the kernel
  • rfl — reflexivity, the simplest proof: "same by definition"
  • ∀ (forall) — "for every" — universal quantification over all values
