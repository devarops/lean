Lean Glossary

A quick-reference glossary of Lean and type-theory terms used across these lessons.

Type (noun)
A classification of data that tells Lean what kind of value something is. Examples: Nat (natural numbers), String, Bool. In Lean, every expression has a type, and the compiler checks that types are used consistently.
See also: Lesson 1: Specs Are Types
Type Checker (noun)
The part of Lean that verifies every expression has the correct type before the program runs. This is your specification checker — if a function claims to return a Nat but actually returns a String, the type checker catches it.
Specification (noun)
A precise description of what a program should do. In Lean, the type signature of a function is its specification. For example, add : Nat → Nat → Nat specifies "a function that takes two Nats and returns a Nat." More expressive specifications use dependent types and theorems.
See also: Lesson 1: Specs Are Types
Function (noun)
A mapping from inputs to outputs. In Lean, functions are pure — they always return the same output for the same input, and have no side effects. Defined with def.
See also: Lesson 1: Specs Are Types
def (keyword)
Used to define a function or constant in Lean. Syntax: def name (args : Type) : ReturnType := body. Example: def double (x : Nat) : Nat := x + x.
#eval (command)
Evaluates a Lean expression and prints the result. Like Python's print() or the REPL. Example: #eval 2 + 2 prints 4.
#check (command)
Shows the type of any expression. Example: #check "hello" prints "hello" : String. Your most important debugging tool for understanding types.
Oracle (noun)
An executable reference implementation that always produces the correct output. In spec-driven AI development, you write the oracle in Lean, and the LLM generates code that should match it. Example: doubleSpec is an oracle for the "double a number" task.
See also: Lesson 2: Executable Specs
Validator (noun)
A function that checks whether an implementation matches an oracle for selected test cases. Returns true if the implementation passes all checks, false otherwise. Example: a validator might test an LLM's max implementation against maxSpec for 5 representative inputs.
See also: Lesson 2: Executable Specs
Nat (type)
The type of natural numbers: 0, 1, 2, 3, … Unlike Python ints, these are unbounded (no overflow). They are defined recursively: zero and successor.
String (type)
The type of text strings. Written in double quotes: "hello". String interpolation: s!"Hello, {name}!".
Bool (type)
The type of boolean values: true and false. Note: lowercase in Lean (unlike Python's True/False).
Pattern Matching (noun)
A way to define a function by cases. Instead of if/else, you list the possible shapes of the input and what to return for each. Example: 
def isZero (n : Nat) : Bool :=
  match n with
  | 0 => true
  | _ => false
Pure (adjective)
Describes a function that has no side effects — it only computes its return value from its arguments. No mutable state, no I/O, no exceptions. Pure functions are predictable and testable.
Proposition as Types (concept)
The core idea of the Curry-Howard correspondence: a proposition (a statement that could be true or false) is represented as a type, and a proof of that proposition is a value of that type. This is how Lean unifies programming and proving.
Covered in later lessons.
Curry-Howard Correspondence (concept)
The deep idea that programs and proofs are the same thing:
  • Types ↔ Propositions (specifications)
  • Programs ↔ Proofs (evidence that the spec is met)
  • Function application ↔ Modus ponens
Covered in later lessons.
Dependent Type (noun)
A type that depends on a value. For example, Vec T n could be the type of vectors of length n containing elements of type T. This lets you encode properties like "this list has exactly 3 elements" in the type itself.
Lake (noun)
Lean's build system and package manager. Like Python's pip + make. Commands: lake build, lake new, lake run.
Elan (noun)
The toolchain manager for Lean (like rustup for Rust or pyenv for Python). Installs and switches between Lean versions.
LSpec
A testing library for Lean used in this workspace's katas. Similar to Python's pytest. Assertions like LSpec.test "name" (actual = expected).
Theorem (noun)
A proposition whose truth is checked by Lean's kernel. Defined with the theorem keyword — same syntax as def, but the body is a proof instead of a computation. Example: 
theorem double_eq_add_self (n : Nat) : double n = n + n := rfl
Read as: "For every n, double n equals n + n."
See also: Lesson 3: From Testing to Proving
rfl (proof term)
Short for reflexivity. The simplest possible proof: it asserts that two sides of an equality are definitionally equal — they reduce to the same expression when the compiler unfolds all definitions. Works only when the equality is "true by definition." Example: theorem foo (n : Nat) : n + 0 = n := rfl fails because n + 0 does not reduce to n for variable n.
See also: Lesson 3: From Testing to Proving
∀ (Universal Quantifier) (symbol)
Pronounced "for all" or "for every." A binder in a proposition that says the statement holds for every value of the given type. In practice, you see it in the type of a theorem: 
double_eq_add_self (n : Nat) : double n = n + n
The (n : Nat) binder is syntactic sugar for ∀ (n : Nat), .... The proposition is: "for every natural number n, double n equals n + n."
See also: Lesson 3: From Testing to Proving
Definitional Equality (concept)
Two expressions are definitionally equal when the compiler can tell they're the same just by unfolding definitions and computing basic reductions — no reasoning required. This is what rfl proves. Example: double n and n + n are definitionally equal because double is defined as n + n. Contrast with propositional equality, which requires a proof.
Kernel (noun)
The small, trusted core of Lean that checks proofs. Everything else — tactics, automation, the elaborator — can have bugs, but the kernel is minimal and verified. It's the final authority on correctness.
